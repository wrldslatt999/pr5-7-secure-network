# Звіт до ПР №5–7 «Розробка безпечних мережевих застосунків»

**Виконав:** Чучула Євгеній Андрійович  
**Предмет:** Прикладні аспекти програмування  
**Реалізація:** Python 3.11+, TCP/HTTP(S), TLS, SQLite, Docker Compose, GitHub Actions.

## 1. Два вузли й топологія

Підготовлено `compose.yaml`: два окремі сервіси `server` (172.28.57.10) та `client` (172.28.57.11) у мережі 172.28.57.0/24. На вузлі сервера TCP 8080 (HTTP) і 8443 (HTTPS); назовні порти лише на localhost хоста. У файлі [TOPOLOGY.md](TOPOLOGY.md) є схема, SAN сертифіката та команди для перевірки адрес. **Фактичне розгортання двох контейнерів у Kali ще необхідно підтвердити окремими результатами**, тому YAML не подається як уже виконаний експеримент із двома вузлами.

## 2. Нешифрований протокол

Розроблено JSON API `POST /echo-http`, який повертає отримане повідомлення у полі `echo`. Обмежено 4096 байтів. HTTP використовується лише для навчальної демонстрації; маршрути з обліковими даними/токенами повертають 426 без TLS. Тести `test_http_echo_roundtrip`, `test_server_refuses_plaintext_auth` проходять через TCP.

## 3. TLS, CA і перевірка автентичності

`scripts/gencerts.sh` генерує локальний CA та серверний сертифікат із `subjectAltName` (DNS: `server`,`localhost`; IP: `127.0.0.1`,`172.28.57.10`). Сервер встановлює TLS 1.2 як мінімум; клієнт використовує `ssl.create_default_context(cafile=...)` і перевіряє ім'я хоста. У тестах з правильним CA з'єднання успішне, із незалежним CA виникає `CERTIFICATE_VERIFY_FAILED`. Сертифікати створюються локально та не потрапляють до репозиторію.

## 4. Облікові записи та ролі

Облікові записи створюються локально (`tools/setup_lab.py add-user`) у SQLite. Паролі зберігаються як scrypt-хеш із випадковою 128-бітною salt, параметрами n=131072,r=8,p=1 (для CI застосовано дешевше n=16384 через окрему тестову змінну). Сервер розрізняє `user` та `admin`. Роль у JWT не визначає доступ — вона повторно звіряється за SQLite; спроба `user -> /admin/overview` дає 403.

## 5. Сесії/JWT

JWT HS256 підписано випадковим секретом із `.env`, який не має стандартного запасного значення. Claims: `sub`, `iss`, `aud`, `iat`, `nbf`, `exp`, `jti`, `mfa`. Типовий TTL = 900 секунд. Сервер відмовляє (401), якщо токен прострочений, підпис змінений, `alg:none`, jti відкликаний у SQLite або для користувача, який увімкнув MFA, ознака MFA у токені відсутня. Logout зберігає jti в таблиці revocation.

## 6. Логи

`logger_setup.py` формує JSONL: timestamp UTC, назва події, user, ip, path, status, latency. `tools/analyze_logs.py` фільтрує за часом, подією, користувачем. Без паролів, OTP, JWT і body. Додаткові пояснення у [LOG_ANALYSIS.md](LOG_ANALYSIS.md).

## 7. Захист brute force

Клас `RateLimiter` (потокобезпечний) відхиляє після 5 спроб входу на обліковий запис у 60 секунд із кодом HTTP 429; додатково обмежує спроби з IP. Обмеження для `/echo-http`: 250 запитів/с на IP (локальна політика). Інтеграційний тест надсилає 7 помилкових логінів та перевіряє 5×401 + 2×429. У користувацькому CLI доступний `brute-demo` лише проти навчального сервера та максимум 15 спроб. Це захист від **обмеженого** перебору, не від масштабної DDoS-атаки.

## 8. MFA

Увімкнення TOTP виконується у два етапи: `mfa-setup` (авторизований токен + повторний пароль) і `mfa-confirm` (правильний одноразовий код упродовж 10 хвилин). TOTP: HMAC-SHA1, 6 цифр, 30 секунд, допустимий часовий дрейф ±1 інтервал, сервер зберігає `last_totp_step` і не допускає повтору OTP. Після підтвердження старі сесії без MFA не працюють. Інтеграційний тест охоплює цю послідовність. Локальна SQLite не шифрує секрет TOTP, що окремо зафіксовано як обмеження.

## 9. CI/CD

`.github/workflows/security.yml`: при `push`/`pull_request` запускаються Python 3.11/3.12, перевірка синтаксису, статичний AST-сканер (`verify=False`, `exec`/`eval`, літеральні секрети), unit + TLS tests. Помилки **не ігноруються**. Локально пройдено 29 тестів і 0 статичних findings. **Останній статус GitHub Actions потрібно зафіксувати після публікації**.

## 10. Аналіз TLS/HTTP, результати та рекомендації

У файлі [../benchmarks/results.md](../benchmarks/results.md) містяться **фактично отримані** виміри на локальному Linux-середовищі підготовки проєкту, 20 запитів для кожного протоколу/розміру, 16/1024/2048 байтів. Методика: окреме TCP-з'єднання для кожного запиту, перевірка тотожності відповіді, HTTPS з перевіркою CA, p50/p95/req/s. Вимір включає TLS handshake, тому не слід інтерпретувати різницю як чистий час шифрування.

У локальних вимірах HTTPS повільніший на малих повідомленнях через створення TLS-сеансу; його перевага — конфіденційність і автентичність каналу. HTTP використовувати лише як навчальну базову лінію. На продуктивність впливають CPU, бібліотека SSL, версія Python, процеси та мережа. **Виміри з Kali потрібно провести окремо**, перш ніж називати їх результатом Kali.

**Рекомендовано:** перейти на TLS 1.3 з reverse proxy, централізувати rate limiting та сесії, застосувати Argon2id/KMS, запровадити більш надійний MFA (WebAuthn/passkeys), розширити CI перевірками Bandit/CodeQL і динамічними тестами та контролювати логи за політикою зберігання. Повний перелік ризиків — у [SECURITY.md](SECURITY.md).

## Висновки

Створено робочий навчальний прототип, що підтримує контрольовану незахищену передачу, TLS-з'єднання з верифікацією CA, парольну автентифікацію, RBAC, JWT, MFA, лімітування та журнали. Автоматизовані тести демонструють коректне відхилення типових порушень доступу і наявність TLS. Двовузлова топологія спроєктована у Docker Compose; для повного виконання пункту 1 її слід фактично підняти й задокументувати в Kali Linux. Система потребує додаткового аудиту перед використанням поза навчальним середовищем.
