# Безпека рішення та обмеження

| Механізм | Реалізація | Перевірка/обмеження |
|---|---|---|
| TLS | `ssl.SSLContext(PROTOCOL_TLS_SERVER)`, мінімум TLS 1.2; локальний CA, SAN і перевірка довіри | Тест правильного і стороннього CA; не робити `verify=False` |
| Розділення протоколів | HTTP допускає лише `/health` і `/echo-http`; захищені маршрути повертають HTTP 426 | Реальний HTTP-тест; не надсилати паролі в HTTP |
| Паролі | `hashlib.scrypt` із випадковою salt 16 B, n=2^17, r=8, p=1, 32 B | Немає plaintext password у SQLite, повтори дають різні хеші; тести швидкості використовують дешевший, але безпечний мінімальний параметр n=2^14 |
| JWT | HS256 HMAC із випадковим секретом ≥32 B, строго фіксований алгоритм, `iss`, `aud`, `iat`, `nbf`, `exp`, `jti` | 401 для невалідної сигнатури, `alg:none`, простроченого та відкликаного токена; 900 с TTL |
| Авторизація | Сервер дивиться роль у SQLite при кожному запиті, не довіряє ролі з клієнтського запиту | 403 для user на `/admin/overview` |
| MFA | TOTP 6 цифр/30 с, двоетапне підключення з повторним паролем, захист від повторного використання коду | Сервер не приймає токени без MFA після активації; 401 на відсутній/повторений OTP |
| Brute force | Рівень ліміту `5` спроб на користувача за 60 с та `15` спроб на IP (стандартні значення) | Реальні тести 429; IP береться із сокета, не із `X-Forwarded-For` |
| Logging | JSONL: UTC timestamp, event, username, path, IP, HTTP code, latency | `tools/analyze_logs.py`: фільтри; не зберігає тіло, паролі, токени чи OTP |
| CI | AST-перевірка на `verify=False`, `exec`/`eval` і літеральні секрети; compile+unit+TLS tests | Workflow **падає**, коли перевірка виявляє проблему; не використовується `|| true` |

## Модель загроз і залишкові ризики

- **MITM:** перевірюваний CA і SAN захищають від підміни сервера лише якщо CA-корінь сам захищений. Локальний CA — не загальнодовірений.
- **Brute force / password spraying:** ліміти діють лише в пам'яті одного HTTPS-процесу. Масштабування на багато worker-ів потребує централізованого Redis/шлюзу. Атакувальник може навмисно заблокувати логін жертви на 60 с — це обмеження policy.
- **Resource exhaustion / DDoS:** JSON не більше 8192 B, echo не більше 4096 B, обмеження echo, таймаут сокета, обмеження паралельного scrypt 2. Це **не повноцінний захист від DDoS**: ThreadingHTTPServer створює потоки на з'єднання; потрібен reverse proxy, connection caps, WAF, iptables/nftables та моніторинг.
- **MFA secret at rest:** TOTP secret зберігається у приватній SQLite-базі (права 0600), **без додаткового шифрування**. Для production необхідне шифрування на рівні KMS/HSM/сервера та політика резервного відновлення; компрометація БД руйнує другий фактор.
- **JWT signing key:** має зберігатися в `.env` поза Git, ротація секрету наразі вимагає керованого перезапуску й інвалідує старі токени. Для production потрібен KMS, kid/JWKS/ротація з двома активними версіями.
- **Library maintenance:** у навчальній версії JWT, TOTP і HTTP обробка написані з використанням стандартної бібліотеки; немає незалежного security audit. Для production використовуйте відомі framework/бібліотеки (FastAPI, PyJWT, pyotp, Argon2id), перевіряйте залежності й TLS-конфігурацію.
- **HTTP plaintext:** зберігається тільки для демонстрації та порівняння продуктивності. Будь-яку автентифікацію через HTTP відхилено; зовнішні з'єднання з хоста не відкриті.
- **Logging:** локальні логи містять IP і username, тому слід обмежувати доступ, визначати строк зберігання і політику видалення; у навчальному проєкті централізоване збирання/SIEM не реалізовано.
- **CI scanner:** AST перевіряє лише конкретні класи заборонених конструкцій, це не SAST загального призначення. Рекомендовано Bandit, CodeQL, Semgrep і залежнісне сканування, якщо підключені сторонні пакети.

## Рекомендації за пріоритетністю

1. Впровадити reverse proxy із TLS 1.3 та автоматизованим керуванням сертифікатами, відключити HTTP після демонстрації.
2. Перенести сесії й ліміти в централізоване сховище, захистити від повторів/розподілених атак, додати redis rate limiting і WAF.
3. Використовувати Argon2id із tuning параметрів відповідно до OWASP, passkeys/WebAuthn або phishing-resistant MFA.
4. Додати ротацію ключів, апаратне/кероване зберігання MFA секретів, аудит залежностей і pentest за погодженим scope.
5. Налаштувати централізоване журналювання з маскуванням PII, alerting для `auth.fail`, `rate.limit`, `auth.mfa.fail` і регулярний security review.
